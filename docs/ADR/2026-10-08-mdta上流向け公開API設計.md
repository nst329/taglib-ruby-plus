# ADR: TagLib上流向けmdta APIを保持・一括置換へ絞る

- 日付: 2026-10-08
- 状態: 採用（設計方針）。上流への適用・投稿・PR作成は行わない。

## 背景

上流masterに今回のmdta専用APIは確認できなかった。ローカルのTagLibパッチには、mdta保持・編集に加え、Rubyの状態移送、プロパティfallback、IOStreamエラー報告が含まれる。このパッチ全体を一つの上流機能として提案すると責務と互換性の検討範囲が広くなる。

## 決定と理由

1. 上流初期案を「既存mdtaの保持」と「キー単位の複数値置換・削除」に限定する。最小の問題と期待結果をレビュー可能にするため。
2. `MdtaValue`と読み取りsnapshotの`MdtaItem`を分ける。setterで値内のkey/indexを無視する契約を避け、入力に不要な識別情報を持たせないため。
3. 公開値クラスはPrivateポインタとexportされたメソッドを使う。既存のItem/CoverArtと形式を合わせ、将来の内部変更を公開レイアウトへ波及させないため。
4. Listで順序と重複を保持し、dataTypeを32-bit wire fieldとして扱う。StringList、enum、Mapによる暗黙の変換や情報損失を避けるため。
5. 上流には一括置換だけを追加し、単一値設定は一要素リストとする。公開setterを重複させず、ローカルの既存setterはadapterで互換維持できるため。
6. `mdtaStatus()`で不在・編集可能・非対応を区別する。非対応構造の空一覧を完全な退避データと誤認させないため。
7. 初期対応を単一mdta metaへ絞り、mdir-only新設と複数meta編集は後続へ分ける。保存先の解決と通常ItemMapの所属を一度に大きく変更しないため。
8. 未対応mdtaが存在する場合はmetadata保存を事前拒否する。通常タグだけの保存でも元情報を壊すことを防ぐため。この挙動変更は公開する。
9. setterでは全体検証・候補構築・swap、writerではkeysとilstを一つの更新計画にする。メモリの部分更新と旧offsetによる不整合を避けるため。
10. 未変更atomはrawを再利用し、変更キーの値だけを正規化する。必要な値の復元と、未知情報の保持を両立するため。
11. 保存後にFile・Tag・chapter処理が共有するatom treeを再構築する。同じFileインスタンスでの連続saveを保証するため。
12. IOStreamへのvirtual追加はmdta提案から分離する。既存カスタムstreamのvtableとABIへ影響し、mdtaの公開API追加だけでは解決しないため。
13. nativeのin-place保存を原子的と説明しない。Rubyの一時コピー・再読込検証・renameは引き続き必要な責務であるため。
14. Ruby専用のcopyStateTo/applyChangesと通常プロパティfallbackを初期提案から外す。上流にbinding固有の公開APIを持ち込まず、個別に契約を検討するため。
15. 移行時の状態移送用下流パッチは別管理する。上流案だけでは現在の安全保存bindingを無変更で置き換えられず、公開一覧からの再構成では未知atomや削除を失うため。
16. upstreamのリリース番号は決めない。ローカル2.3.2.7という番号と、未採用の上流機能を混同させないため。

## 検討した代替案

- ローカルパッチをそのまま上流へ渡す: IOStream ABI、プロパティ連携、Ruby固有処理の議論が混ざるため採用しない。
- 公開structをそのままsetterに渡す: 不要なkey/indexを無視する契約と公開レイアウトの固定が残るため採用しない。
- Mapだけで公開する: keys indexや値なしentryの観測を失いやすく、キーの順序が別の規則になるため採用しない。
- 汎用atom編集APIから実装する: 必要なmdta複数値復元より範囲が広いため、別の要望として扱う。
- 複数meta対応を初期必須にする: 文書ID、通常タグの所属、保存先解決の追加が必要なため後続案とする。

## 影響と制約

上流を想定した公開型は現在のローカルnative型と異なる。既存Ruby APIの外部契約はadapterで維持できるが、native ABIと状態移送の移行作業が別途必要。非対応構造の編集・metadata保存、mdir-onlyへの復元、一般IOStreamの全I/O失敗検出は初期案で完了したとは扱わない。

[詳細設計](../mp4-mdta-upstream-design.md)の受入条件を満たして初めて実装完了とする。設計検証用コードと一時コピー上の試作を追加した。配布対象のnative実装および上流ソースには、この試作を適用しない。

## 試作から追加した判断

- keysの存在もmdta構造の証拠として扱う。handler欠落時にAbsentと誤判定して破壊的な通常保存を許さないため。
- 非numeric itemは既知handler/property登録で分類する。ItemFactoryのisValidは任意fourCCを受理し、対応範囲の証明にならないため。
- tree再構築ではTagとItemMapの公開オブジェクトを維持する。連続保存のoffsetを更新しつつ、既存利用者の参照を不用意に無効化しないため。
- 変更キーのdata子を一つのnumeric親にまとめ、writerと境界検証で同じ長さ計算を使う。順序を明確にし、検証と実出力の不一致を避けるため。
- 字幕等の比較にはstream indexではなくtrack IDを使う。QuickTime chapter追加でstreamの列挙順が変わるため。
- I/O破棄のテストは既知制約の再現として記録する。テスト成功を安全な保存の達成と混同しないため。

試作結果は15テスト、native 36ケース・341アサーション。ABIと全保存後のsnapshot確定などの残課題は[検証記録](../Memos/2026-10-08-mdta上流設計のnative試作検証.md)に明記する。

## 利用者合意に基づく設計整理

非対応構造を変更前に明示的に拒否する方針を利用者が了承した。本体への取り込みは将来の話とし、当面は限定した範囲の実現性と完成条件を明確にする。

- 構造判定、候補編集、保存計画、File保存調整、Ruby原本保護を分ける。検証中の状態変更とI/Oを混ぜず、拒否のタイミングを明確にするため。
- tree更新と成功snapshotの確定を分離する。metadata保存成功後のchapter失敗で、未完了の変更を解除しないため。
- File側で保存全体を調整し、Tag保存内部の確定を延期する。公開transaction APIや汎用writerを新設するより既存責務に沿った小さな変更で済むため。
- Unsupportedでは部分的な一覧を公開せず、metadataと後続chapter保存を事前拒否する。黙った欠落や通常保存による迂回を防ぐため。
- 一般IOStreamの全障害検出を初期機能の完成条件から分離する。現行契約で不可能な保証を実装の成否と混同せず、Rubyの一時保存・照合で原本を保護するため。
- 試作の成功と完成実装の未達を第2節に集約する。文書内の古い「未実装」「連続保存未確認」と実際の検証結果の矛盾を解消するため。

今回のリファクタリングは設計・ADRのみ。試作および配布コードの動作は変更しない。

## 隔離した提案実装での判断

- 一括置換、構造拒否、tree再接続、全保存後の状態確定を単独の提案パッチとして実装する。既存Ruby版のパッチと公開型・責務が異なり、誤って置き換えないため。
- mdtaでは毎回meta全体を一回で更新し、隣接freeの吸収を行わない。keys/ilstの複数書込とpaddingによる増分計算の分岐を減らすため。
- 元の順序付きraw itemを維持し、変更したキーだけ一つの親にまとめる。未変更mdtaを通常ItemMapの並びに巻き込まないため。
- 再読込したmetadata/chaptersと期待値を照合してから確定する。成否を返さないIOStreamでも、失われた書き込みの一部を検出できるため。永続化の保証とはしない。
- chapter増分は保守的な上限で事前検証する。既存chapter writerを複製せず、親サイズやoffsetの桁あふれを防ぐため。境界付近の安全側の拒否を許容する。
- 4GiB超のファイルを一律拒否しない。metadataが表現可能なら保存でき、QTが新設する32-bit stcoでEOFを表現できない場合だけ事前拒否するため。
- 汎用IOStreamのvirtualは変更しない。原始ヘッダーでコンパイルした既存クライアントとcustom streamを使い、限定した互換性を確認するため。

19テスト、native 40ケース・369アサーションが成功。詳細は[隔離実装の検証記録](../Memos/2026-10-08-mdta上流向け隔離実装の検証.md)。配布実装への適用・上流への投稿は行わない。
