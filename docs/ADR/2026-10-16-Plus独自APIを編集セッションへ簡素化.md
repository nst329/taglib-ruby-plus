# Plus独自APIを編集セッションへ簡素化する

日付: 2026-10-16
状態: 採用・初版実装済み。Document/Update/SavePlan公開案に代わる実装。

## 背景

前案をtest専用adapterで具体化し、主要な状態・保存境界は実行できた。一方、通常のタイトル変更でもDocument、MetadataUpdate、SavePlan、SaveResultを理解する必要があった。内部で必要な責務を、そのまま公開概念として増やしていた。

ユーザーのシンプル化の要望を受け、公開オブジェクトと状態遷移を改めて検討した。互換性不要、原本の保持検証と未知構造拒否は維持、製品コードは変更しないという前提を引き継ぐ。

## 推奨する決定と理由

- 編集用Fileと不変snapshotを公開の中心とする。getterは常に現在候補を返すため、通常の「読む・編集する・保存する」で理解できる。
- metadata/chapterの変更はwith/withoutで新値を作って代入する。更新要求のfactory、merge/apply、native setterという複数の編集入口をなくすため。
- 保存はsave!(to:)にまとめ、保存計画・writer選択・検証を内部へ置く。SavePlanの独立所有やclose後の実行は初版の公開要件から外す。通常利用に必須でなく、状態の寿命と再使用規則を増やすため。
- changesは確認用の不変Hashとし、実行可能な計画を兼ねさせない。差分確認と保存可能性の保証を混同しないため。
- 原本保存成功後は検証済み出力値を新baselineとして継続する。候補と再読込結果を公開前に用意し、nativeの公開後reopenに依存しない。毎回Fileを開き直す利用モデルを不要にするため。
- 別出力では原本を更新していないため、元baselineと編集候補を保持する。save-asでFileの参照先を勝手に切り替えたり、保存した値をgetterから消したりしないため。
- diagnose(area)は一領域の固定schema Hashを返す。Report.sectionsの階層とIssue/SaveResultの専用クラスを削る。以前の設計でもHashとメソッド参照が混在し、包装の分だけ利用が複雑になったため。
- 例外はArgumentErrorと共通MP4::Errorを基本にし、code/phase/committed等を残す。例外階層を簡素化しても保存の公開前後・回復判断に必要な情報は削らない。
- 比較は厳密値の==/diffへ絞る。空keys残存の許容は、明示的にclearしたキーに限定する内部保存検証で行う。利用者に保存用の比較modeを選ばせないため。
- 修復は専用の明示的メソッドで保留し、save!で実行する。通常編集との混在は順序を問わず拒否し、修復保留中はchanges/diagnose/save!/closeに限定する。通常snapshotでraw修復後の状態を推測表示しないため。API整理を理由に既存の保持条件を緩めないため。

## 比較した案

| 案 | 評価 |
| --- | --- |
| 完全statelessなread/update(path, hash) | 一回の更新は短いが、複数領域の編集・原本の世代対応・事前確認を引数へ押し込める |
| FileからUpdate/Planの便利メソッドだけを追加 | 初回操作は短くなるが、元の公開クラスと二重の利用モデルが残る |
| mutableなmetadata Hashを直接編集して保存 | 書きやすいが、途中入力・所有コピー・型/locale/空値の扱いを追いにくくする |
| 編集用File＋不変値＋明示的save! | 状態所有は一箇所、値の入力検証と原本保存を分離できるため推奨 |

元ラッパーへ機能を再混入する案ではない。TagLib::Plus::MP4に独自Fileを置き、低水準TagLib::MP4::Fileとは状態を共有しない。公開の抽象を減らすことと、内部の検証を削ることは分けて扱う。

## 検証と制限

初版は`TagLib::Plus::MP4`として実装した。前案のadapterは前案の試作として残し、低水準`TagLib::MP4`とはnative状態を共有しない。原本保存後の継続と別出力後の候補維持は製品APIの利用テストで確認する。

setterの全入力検証、古い診断の拒否、修復と通常編集の逆順混在拒否、保存失敗後の候補維持、公開後失敗時のFile使用禁止を受入条件にする。raw metadataと全media bytes、offset補正、hint等の既存fixtureを引き続き使う。
