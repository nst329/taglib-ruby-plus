# atom編集をサイズ計算と一回の出力生成に分離する

状態: 採用

## 背景

チャプター限定の改善に加え、metadata完全置換、時間修復、併用修復が使う共通atom編集のI/Oを確認した。

MP4AtomEditorはサイズとfree消費を決めるため、moovを3回生成していた。capture_rawがfalseの場合、保持するtrackの名前・sample table等を生成のたびに原本から読み直す。metadata完全置換では、入力検証と編集計画で、後続の検証が使わない保持署名も作成していた。

## 決定と理由

- atomの境界・参照編集・生成済み置換bytesから出力サイズを計算し、paddingとchunk offsetの移動量を決めた後に、一度だけmoovを生成する。サイズ確認のためのpayload読取と文字列の組立てを避けるため。
- atom全体の置換を共通の`@atom_replacements`へ集約する。キーは原本atomの開始offset、値は置換atom全体のbytes。metadata・時間修復・併用修復で、出力サイズ・出力bytes・保持署名の三つが同じ表を参照する。派生editorごとのrender・署名処理をなくし、サイズと出力の食い違いを防ぐため。
- 削除は既存の削除判定をサイズ計算と出力生成で共用する。直下free消費も同じ判定へ寄せる。単なる削除を置換文字列へ変換する仕組みは追加しない。
- metadataの入力構造検証と完全置換の書出し計画は`capture_signature: false`とする。ここで生成した署名は従来から保存後検証に渡していないため。atom境界・対応構造・参照・chunk offset・hint検証は維持する。
- 参照修復・時間修復・併用修復の保持署名は引き続き生成し、保存後の独立解析と比較する。出力のmetadata値・purl raw・必要なchapter値・mdat署名検証と原子公開も維持する。

## I/O・CPU・メモリ

metadata完全置換における保持leafの読取は、以前は入力検証の署名1回、編集計画の署名1回、moov生成3回に加え、コピー時の全体読取1回だった。変更後はmoov生成1回とコピー時の全体読取1回になる。原本全体のコピー1回、出力の独立全体走査1回は維持する。変更対象の旧metadata payloadの読取を省く既存方針も維持する。

サイズ計算はatom数に比例する木の走査で、payloadを読み込まない。moov文字列をサイズ計算用に組み立てないため、CPUと一時文字列の割当も減る。新しいcacheは設けず、境界index・置換bytes・署名の寿命は従来の世代と編集計画に従う。

## 実測

2MiBのtrack udta/nameを保持しながらmetadataを完全置換する合成fixtureで、当該payloadと交差したRuby File#readを計測した。コピーの大きなreadには周辺header等も含む。

| 対象 | 変更前 | 変更後 |
| --- | ---: | ---: |
| 保持payloadと交差するread回数 | 72 | 4 |
| 上記readが返した合計bytes | 12,587,955 | 4,199,287 |
| 入力構造検証での保持payload読取 | 署名用に1回走査 | 0 |
| moov生成 | 3回 | 1回 |

変更前は64KiB単位の署名読取2走査とatom全体の生成用読取3回を含む。変更後の4回はatom生成用read1回と、原本コピー・SHA取得の大きなread3回である。これはRubyの論理I/Oの実測であり、native内部I/O・OS cache・SMBの通信量・実行時間の改善率を示すものではない。

## 検証

`test/plus_mp4_atom_pipeline_test.rb`で、metadata入力検証が保持payloadを読まないこと、生成時に1回だけ取得すること、保存後の名前・metadata値を確認する。別の12ケースで、moov先頭配置の拡大・縮小、free消費、4byte余り、通常・拡張header、stco・co64を検証する。mdat保持と独立したoffset期待値、構造診断も確認する。

既存の併用修復テストは、metadata置換のサイズが共通計算に反映されることと、出力の保持署名が一致することも確認する。公開API、metadata snapshot、chapter snapshot・参照修復の対象テスト後に、全体テストを実行する。
