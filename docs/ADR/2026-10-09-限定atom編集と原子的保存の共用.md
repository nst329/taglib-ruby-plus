# 限定atom編集と原子的保存の共用

状態: 採用・実装済み。

## 決定と理由

- `ChapterReferences`の境界・data reference・chunk offset・対象外payload検証を`MP4AtomEditor`でも使う。時間修復とmetadata作業contextに別の汎用MP4 parserを追加すると拒否条件が分散するため。
- 解析中hookで編集対象のraw atom bytesを作り、既存の不変保存計画へ渡す。計画にnative handleやIOを残さず、失敗後に同じ期待値で再試行できるため。
- 時間修復は参照修復の保存フローを共用する。保存後の参照添字計算だけが異なるため、時間修復では元reportと同じ順序付きreportを比較し、変更atomは期待payloadのsize/hashで比較する。
- moov直下freeだけを消費し、余った領域をfreeとして戻す。不足時はmoovを伸ばして検証済みstco/co64を補正する。未知のpadding配置を再構成しない単純な方式に限定するため。
- metadataではmeta以外の保持signatureと、meta内部のraw保持signatureを分ける。通常itemは意図的に変更される一方、handler・keys・先頭0 item群・contextの順序は保持しなければならないため。
- 通常itemの許可atom名を保持profileに列挙する。nativeは未知4文字名もTextへfallbackするため、nativeで表現可能という条件だけでは設計の未知item拒否を満たせない。
- keysをraw保持計画内でも再検証する。外側のdiagnosticsだけに依存せず、保存に使うraw bytes自体の境界・件数・namespace・UTF-8・重複を確認するため。
- native writerのmillisecond換算を整数の商・余りで行う。従来の最寄りms丸めを保ち、中間乗算のoverflowと浮動小数点精度への依存を避けるため。
- native writerのmdhd/sttsは引き続き32bit、章のchunk tableはstcoに限定する。対応幅を超える入力は保存を拒否し、無関係な64bit reader/writer拡張を混ぜないため。
- チャプター自体のco64はstrict/native readerの従来制約として拒否する。動画・音声側のco64補正は検証するが、nativeが読めない章を保存成功と扱わないため。
- native private builderの変更を`0004-mp4-chapter-movie-duration.patch`として配布し、通常ビルドとgrouped検証ビルドに組み込む。Rubyソースだけ更新して生成不整合が残る状態を避けるため。

## 影響

既存`save`は引数なしのまま。参照修復・時間修復・metadata保持保存は別操作とする。完全metadata snapshotはindex 0を引き続き拒否する。実ファイルはテストコピーだけを変更し、外部原本のSHA-256不変を確認する。
