# 限定修復と全体I/O見直しの検証

日付: 2026-10-20

## 対象

壊れたQuickTime専用参照・text trackと、keys範囲外のmdta index itemを一つの候補へ合成する公開APIを実装した。その後、関連全体のRubyラッパー・診断・snapshot・保存を確認し、MP4の重複I/Oを削減した。実ユーザー原本・作品DB・FFmpeg運用フローは変更していない。

## I/O比較

比較元はHEAD dcdfcd1のlibを一時ディレクトリへ展開したもの。比較先は作業ツリー。両方へ同じローカルnative bundleを接続し、Ruby 4.0、通常statモード、同じfixtureを使った。

計測器は既存test/performance/io_meter.cをclang -dynamiclib -O2でビルドし、DYLD_INSERT_LIBRARIESとPLUS_IO_METERでRuby/native両方の論理read/writeを計測した。これは物理ディスク転送量ではない。fixtureの作成・copyは計測開始前に行う。

structural_readsは章/参照/時間/色診断、形式別chapter読取、chapter sample観測を2周する。cached_snapshotsはmetadataとchaptersを取得後、両snapshotを要求した無変更saveを2回行う。

| fixture | 操作 | 変更前read bytes | 変更後read bytes | native open 前→後 |
|---|---|---:|---:|---:|
| test/data/mp4.m4a（12,037 bytes） | structural_reads | 54,019 | 1,402 | 9→0 |
| 同上 | cached_snapshots | 19,612 | 9,122 | 4→2 |
| 8MiB画像付き（8,397,540 bytes） | structural_reads | 109,065,558 | 1,402 | 9→0 |
| 同上 | cached_snapshots | 33,561,624 | 16,780,128 | 4→2 |

全行でwrite bytes、全媒体copy、全体hash、外部process起動は0、errorなし。画像付きfixtureは独立fixture editorでcovr/dataへ8MiB payloadを入れたもの。実画像デコードや再生品質を検証するfixtureではない。

```sh
clang -dynamiclib -O2 test/performance/io_meter.c -o /private/tmp/taglib_limited_io_meter.dylib
python3 test/performance/run_plus_mp4_io.py \
  --ruby /opt/homebrew/opt/ruby/bin/ruby \
  --meter /private/tmp/taglib_limited_io_meter.dylib \
  --before-lib /private/tmp/taglib-limited-io-y13zx3uf/lib \
  --after-lib /Users/nasu/Projects/taglib-ruby/lib \
  test/data/mp4.m4a /private/tmp/taglib-limited-io-y13zx3uf/artwork.mp4 \
  --operations structural_reads cached_snapshots
```

一時pathは今回の作業環境固有であり、再現時には同じ条件のlibとfixtureを用意する。時間は補助値として取得したが、反復分布や速度保証には使わない。

併用修復は正常/metadataのみ/QuickTimeのみ/両方/処理不能、許可不足、最新計画の所有session、世代変化、別出力制約、raw metadata/mdat/Nero保持、snapshot要求、保存結果digest、改変拒否と再試行、公開後cleanup失敗とGCを検証した。
I/Oテストでは計画のmoov全面read1回、取得済みmoov内の再readなし、候補copy1回＋独立scan1回、出力構造解析1回を確認した。構造観測がnative Fileを一度も開かないことと、無変更snapshotでも外部変更時は拒否することを確認した。

## 未検証範囲

実ユーザーファイル、別のnative backendでの再ビルド、4GiB超の併用fixture、任意producerのfourcc/index解釈、電源断・ACL・外部writer完全排他は今回の検証完了範囲に含めない。既存のco64/offset/hint等の対象回帰テストと、併用専用の巨大実ファイル検証は区別する。
mdta_layoutは呼出側が入力の生成規約に合わせて明示する。不明な規約をfixtureの成功から推定しない。strictモードの追加SHA走査は今回の論理I/O表に含めない。

## runner・配布物の確認

`BUNDLE_PATH=/private/tmp/taglib-plus-refactor-gems bundle exec rake test`でtest-unit全体は成功したが、minitestへtest-unit専用引数が渡り起動が失敗した。Rakefileのrunner別オプションを修正後、未実行の`test:minitest`だけを実行して成功を確認した。製品コードはこの間変更していないため、成功済みtest-unit全体は繰り返していない。

最初のPlus全体実行で見つかった既存stscテスト2件のブロック結合ミスも修正し、配列の実値を検証できることを確認した。cleanup失敗のGC競合は失敗原因を特定して明示管理Fileへ変更したもので、世代チェックを緩める回避策は入れていない。

新しいRuby実装・テスト・設計・ADR・検証メモをgemspecへ追加した。作業ツリーのtracked/untrackedファイルとgemspec一覧の一致、gem build成功、新規実装・テストの同梱を確認した。build先は`/private/tmp/taglib-ruby-plus-limited-repair.gem`で、versionは既存2.3.2.31のまま。公開用リリースやversion更新は実施していない。

標準環境のBundlerには開発依存が欠けていた。shoulda-contextを一時領域へ取得した後、既存の完全な開発gem群を`/private/tmp/taglib-plus-refactor-gems`に確認し、標準Rake検証にはそちらを指定した。Gemfile.lockや全体gem環境は変更していない。構文チェックとgit diff --checkも成功した。

## 2.3.2.32のリリース検証

追加指示によりBUILDを32へ更新し、GitHub Packagesへarm64-darwin／x86_64-darwin／sourceを公開する。既存native-gems workflowをv2.3.2.32タグから実行する。CI smokeにも正常入力のplan_limited_repairsがunchangedである検証を追加し、新規Ruby実装の同梱を両CPUで確認する。

ローカルarm64版は既存パッチ済みTagLib、全extension bundle、ABIシンボル照合、再配置した依存libraryを用いてbuildした。stage_repositoryはgit ls-filesを使うため、新規ファイルをindexへ登録してから最終パッケージを生成した。ローカルGemfile.lockは管理対象外のため、version追従だけを行いcommit対象にはしない。

一時gem環境へ2.3.2.32をインストールし、DYLD_LIBRARY_PATHに依存せず同梱bundleを読み込むことを確認した。インストール先のRubyコード・bundleでPlus全体126 tests / 109,948 assertionsとmetadata受入16 tests / 111 assertionsが成功した。これはcheckoutのlibを参照する検証とは別に実施した配布境界の確認である。
