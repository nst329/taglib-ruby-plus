# 複数tref修復と時間診断の検証

## 前提と環境

macOS arm64、Ruby 4.0.7、FFmpeg／ffprobe n9.0.2。実ファイルの場所・bytesは提供されていないため、映像mpeg4、音声aac、字幕tx3g、chapter textを含む合成fixtureを使用した。実ファイルのhvc1映像、sample分布、生成履歴まで同一ではない。実ユーザーファイルへの書込みはしていない。

ローカルlibのnative bundleはmetadata snapshot非対応で、既存テストもfixture生成で失敗した。対応済みの隔離native bundleを利用し、現在のRubyコードを/private/tmp/taglib-multi-tref-validation/libへコピーした。最終関連検証はcopyright-cpy-binding-legacyのnative、grouped検証はcopyright-cpy-binding-groupedのnativeを使用した。nativeの再ビルドや置換、上流個別コミットの検討は行っていない。

複数ファイルを同じrunnerへ読込む場合、一部テストがLOAD_PATH先頭にリポジトリlibを追加するため、隔離libのtaglib/baseとtaglib/mp4を事前requireする。事前requireなしの初回関連検証は、非対応bundleを読み込みfixture生成等で失敗した。最終結果として扱っていない。

## 原因の再現

HEADの変更前mp4_chapter_references.rb／mp4_chapter_reader.rbを隔離libへ配置し、新しい複数trefテストを実行した。1 test / 2 assertions / 1 errorでduplicate tref atomを再現。ChapterReferences#collect_referencesからchild(track, 'tref')、oneの単一atom制約に到達して停止する。

## 必須検証との対応

- 欠落→有効、有効→欠落の別trefを両方テスト。映像・音声・字幕の欠落0を除去し、音声からtext chapterへの参照を保持。
- 複数trak、同一chap内の有効／欠落混在、有効IDの重複・順序・複数trefのまとまり、hint参照、元から空のtref／chapを独立parserで確認。
- 診断は元tref_indexを返す。削除後の位置とchap内の位置を保存検証。flat参照が同じでもtrefを統合した出力はverifyで拒否。
- 重複chap、実Track ID重複、chap payload不整合、不正atom境界、未知／fragmented構造、外部dref、mdat外offsetを拒否し、原本digestを比較。
- stco／co64、moovがmediaの前／後、拡張moov header、4 bytes除去のfree不足による8 bytes移動を検証。offsetのmdat相対位置と全media bytesを保持し、stcoの移動例はFFmpegデコードでも確認。
- 保存計画作成時は原本digestが不変。同一計画の再実行、保存後再実行は空。保存・別handle再読込・chapter_snapshot・通常タグ保存後のchapter保持を確認。
- 書込失敗、保持対象media破損、一時atom解析不能、置換失敗を注入して拒否・原本保持・cleanupを確認。書込失敗後に再試行成功。
- 書込＋cleanup失敗を注入し、phase=:cleanup、committed=false、causeに元の失敗、残った一時コピーを確認。障害解消後の再保存で成功し一時パスが消える。
- 置換後の再open失敗はphase=:reopen、committed=true。新handleで修復済みchapterを再読込できる。native handleが既にcloseされるためこの故障注入はFile.newで検証する。既存File.openブロックのensureが二重closeするとObjectPreviouslyDeletedになり得る問題は今回の変更範囲外として残る。
- 全mdat、chapter sample bytes、tkhd／mdhd／elst／stts等の時間情報、Nero、metadata、artwork、実Track ID、字幕nameのraw leafサイズ・hashを比較。
- 正常な時間fixtureはeditなし、単一edit、トリミング、empty edit＋複数edit、rate変更、rate=0、version1を検証。正常editのmedia/movie duration差を不整合にしない。truncated elstを拒否し原本不変を確認。

## 提示された時間不整合

mvhd v1 scale=441000000／duration=1605653349300、mdhd scale=1000／duration=3640937、stts16サンプル合計3640937、tkhd v0 duration=3640937、elst v0 duration=0xd865c3b4を再現した。実サンプルも16件で、時刻0の空タイトルpaddingを除いて厳密readerが15章を読む。参照修復前後で時間診断の値は完全一致。

観測はtkhd_elst_duration_mismatchとelst_matches_movie_duration_low32。tkhd durationは約0.008256秒、elstは約8.232535秒、media/movieは約3640.937秒になる。下位32bit一致は観測事実であり、生成時のoverflowを確定したものではない。

同じ合成fixtureに全トラックの欠落0＋音声の別tref有効参照を注入して修復後にffprobe -show_chaptersを実行した。n9.0.2では終了成功、stderr空、16章を返した。厳密readerは15章。実ファイルで報告されたffprobeの1章表示は再現できず、paddingの扱いにも差がある。合成fixtureは時間フィールドの診断と保持を検証するもので、実ファイルの症状全体を再現するものではない。

## 未検証と残る制約

実ファイルの解析・修復・ffprobe再現、生成ソフトと書込履歴、正しいedit mapping／補正値は未確認。動画codec、chunk配置、実際のsample duration分布、FFmpeg version差も切り分けていない。Linux／Intel／Ruby3.2、新nativeビルド、gem作成・公開は未実施。

参照修復後も時間不整合は残る。複数の有効chapter参照や音声以外からの有効参照、co64 chapter、対応外edit等は保持されるが、厳密reader／snapshot／通常保存の既存制限で拒否され得る。時間診断の観測が空でも全edit mappingの正しさ・正常な再生を保証しない。未知・暗号化・fragmented構造、外部dref等の参照修復の対応範囲も変更しない。
