# Plus独自API設計のテストコードによる確認

日付: 2026-10-16
対象: Document / Update / SavePlanを中心とした前案

後続の[簡素化案](../taglib-ruby-plus-api-redesign.md)では編集用Fileと不変値・save!へ変更している。本記録のテスト成功は前案と共通する保存境界の検証結果であり、簡素化案の公開API・保存後状態を実装/実行したものではない。

## 結論と検証の位置付け

保存済みDocumentと独立した更新値・保存計画に分ける主要フローは、合成MP4と既存backendを使う設計用adapterで実行できた。テスト化で不明確だった戻り値と保存照合を具体化し、設計書へ反映した。

これは実装前の履歴記録であり、現在の`TagLib::Plus::MP4`の受入テストではない。`test/support/plus_api_design_probe.rb`の名前空間は`PlusAPIDesignProbe`で、現在のTagLib::MP4を内部で利用する。名前付き新値、一般的な新writer、修復機能を実装したように見せるmockは置かない。

テストは`test/plus_api_design_probe_test.rb`。video/audioと両chapter形式、mdtaの文字列・binary・locale・空キーを持つ短いMP4をffmpegと現行APIで生成する。ユーザーの実ファイルや外部リポジトリにはアクセスしない。

## 確認した契約

| 項目 | 実行した確認 |
| --- | --- |
| 保存前の確認 | Update.applyで期待値を作り、plan/previewで原本とDocumentの値が変わらない |
| 自動保存の禁止 | openブロック終了ではcloseだけを行い、commitなしで原本digestが不変 |
| handleから独立した計画 | DocumentをcloseしてGC後にcommitし、新handleで値を確認 |
| 世代の固定 | 外部変更後のread/plan/commitと、commit後の旧Document・旧計画を拒否 |
| 更新要求の競合 | 独立したmdta更新はmergeでき、property正規化と同じmdtaキーの設定は両方向で拒否 |
| 明示的削除 | nilを拒否、空文字は空値、removeでのみ通常itemを削除 |
| mdtaの空状態 | 不在・空キー・空payloadを区別し、既存キーのclearは[]、不在キーのclearは不在 |
| 全体復元 | 復元先だけの値を消し、明示的に消したキーの空エントリ残存だけを許容 |
| 入力後半の失敗 | 最後のpropertyが不正でも、原本と作成済み計画は使える |
| chapter省略 | Neroだけを空配列にするとQuickTime・metadata・mediaを保持 |
| 別出力 | source不変、出力を独立再読込。変更なしなら全bytesのdigestも一致 |
| 非上書き | 原本自身・既存出力・hardlink・symlinkを拒否 |
| 公開直前の競合 | exists検査後に現れた出力もlink公開で上書きしない |
| media破損 | backend保存後にmdatを壊し、再読込検証で拒否。原本と計画を保持し再試行成功 |
| 未編集空キーの消失 | keys名を同じ長さの別名へ実際に改変し、緩い値比較ではなく保持照合で拒否 |
| 保存中の原本変更 | publish前の世代不一致をverifyのSaveError・committed=falseで報告 |
| cleanup失敗 | 原本を維持し、一時pathと元のverify失敗をcauseに残す。障害解除後に再試行成功 |
| 公開後の失敗 | 結果作成を故障させてもcommitted=trueとし、原本の新値を確認。旧計画の再実行を拒否 |

期待値は手書きのタイトル・空配列・元のtyped mdta・chapter列で照合する。adapterと同じapply結果の一致だけを成功条件にしない。全mdatのdigestとtrack IDも独立fixture parserで比較する。故障は実際の候補ファイルに注入し、偽backendが返すtrueを検証結果として扱わない。

## 見つかった問題と設計の明確化

### 診断sectionの形式不一致

設計書はsectionをHashと定義しながら、利用例では`.data`を呼んでいた。利用例を`report.sections.fetch(area).fetch(:data)`へ修正した。これは静的な利用コードの確認で見つかった問題で、Reportの製品実装を実行したという意味ではない。

### 空mdtaキーの保存照合

初回は16 tests / 112 assertions、失敗0・エラー1。snapshot全体の復元後、復元先だけにあったmdtaキーが空エントリとして残り、全体の厳密比較が拒否した。

原本に存在して期待値から明示的に除いたキーだけを許容対象として固定し、実際の値が空の場合に限り、照合上の除外を認めた。値が残れば失敗。未編集の空キーが失われたり別名になれば失敗。全体をsame_values?で比較する回避策は採用しない。

clearのapply結果も、既存キーは[]、不在キーは不在のまま、と明記した。物理keys削除の保証は追加しない。

### 変更なし別出力

変更なしcommitは原本を置換しない。別出力ではファイルを作る必要があるが、native writerに通すと要求していない再シリアライズを起こし得る。変更なしは単純コピーとし、source/output digestの一致を確認する契約にした。

### cleanupと公開後失敗

cleanup失敗は元のverify失敗を隠さず、phase=:cleanupとtemporary_path、causeを保持する。公開後の結果作成失敗はcommitted=trueであり、元計画を自動再実行しない。この二つを別テストにした。

パスの確認では、macOSの/varから/private/varへのrealpath展開により、当初のテスト期待値が1件不一致だった。sourceはDocumentで解決した実pathとして扱い、テスト側を実path比較に修正した。保存処理の失敗としては扱わない。

## 実行結果（前案の記録）

- 設計probe単体の最初の成功状態: 20 tests / 144 assertions、失敗・エラー・省略0。
- 公開後失敗の1件を追加した最終状態は、関連テストと同じプロセスで実行した。
- 最終: 新規21件を含む84 tests / 1,054 assertions、失敗0・エラー0・省略0。
- 同時実行した既存テストはmp4_snapshot_access_chapter、mp4_chapter_reference_selection、mp4_chapter_references。
- 新規Ruby 2ファイルとgemspecの構文チェック成功。
- 製品コードは変更していないため、全体suiteは再実行せず、設計probeと接続領域のテストを実行した。

```sh
DYLD_LIBRARY_PATH=/opt/homebrew/lib/ruby/gems/4.0.0/gems/taglib-ruby-plus-arm64-darwin-2.3.2.19/lib/taglib_plus/native/arm64-darwin \
/opt/homebrew/opt/ruby/bin/ruby -Ilib -e \
'require_relative "test/plus_api_design_probe_test"; require_relative "test/mp4_snapshot_access_chapter_test"; require_relative "test/mp4_chapter_reference_selection_test"; require_relative "test/mp4_chapter_references_test"'
```

## このprobeで確認していないこと

- 新名前空間のexport・旧API削除・名前付きMetadataItem/MdtaValue/SaveResult等の製品モデル・nativeなしのvalues require。probeでは既存snapshot/Chapter、mdta値Hashと結果Hashを使用する。例外の全code/area/issuesの外形も未実装で、検証に必要な保存phase/committed/pathを具体化している。
- 修復計画・source token・統一Report/Issueの実装。参照・hintの既存テスト成功は、新APIでの修復フロー成功とは区別する。
- raw purl・複合context・未index mdta等のwriter選択と保持方針の移行。
- QuickTime chapterの追加/変更。probeの実保存はmetadataとNero更新に限定して確認した。mdat完全保持の照合は、QuickTime再生成で意図したchapter payload変更の検証にはそのまま使えない。
- 新writerのfile属性・permissionエラー・全cleanup段階・OS/ファイルシステム差異・非協調writerとの完全排他・電源断耐性。
- 全9 Item型・全比較規則・raw付帯情報失効・配布gemの受入条件全体。

以上は製品実装時に別の受入テストが必要。設計probeの成功を次期API全体の実装完了や保存安全性の全面的証明として扱わない。
