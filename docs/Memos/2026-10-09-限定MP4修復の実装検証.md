# 限定MP4修復の実装検証

## 検証環境と前提

macOS arm64、Ruby 4.0.7、ffmpeg/ffprobe n9.0.2。2.3.2.11のRubyコードを隔離bindingへコピーし、legacy/groupedのnative sourceに0004を適用してcmake再ビルド・隔離installした。private builder変更でABIを変更しないため、各prefixへリンクした対応済みbindingを使用した。Homebrew・リポジトリのインストール済みbundleは置換していない。

製品実装前に調査テストと試作を実行し、設計を記録した。その後、製品APIに組み込んで下記を確認した。

## 製品APIで確認した内容

- 複数trefの独立解析、逆順、混在ID、重複・順序・group保持、他参照保持、削除後の添字変化とgroupを含む保存検証。
- 時間profileの明示指定、正常short editの非補正、pending更新拒否、計画前の原本不変、計画後source変更拒否。
- tkhd/elstの64bit補正、creation/modification、flags、ID/reserved/matrix、mvhd/mdhd/sttsと全mdatの保持、保存後の通常タグ保存・再読込。
- moovがmediaの前後、動画・音声のstco/co64、free消費と不足による20byte拡張、整数幅overflowの拒否。章自体のco64は対応外として拒否。
- native新規生成のmovie/media単位差、32bit境界のv0/v1選択、高timescaleでの15章＋padding保持、未知duration/zero timescale/media時間幅超過の保存拒否。
- index 0 raw群の件数・順序・重複・bytes保持、通常title更新2回、ファイルmode保持。index 0の診断と完全snapshot拒否が残ること。
- rawのdrop/reorder/duplicate/payload改変検出、不正keys・未知通常atom・有効numeric混在・非0範囲外・代理空キーの編集拒否。
- native書込・raw再挿入・検証の故障で原本とpending更新を保持し再試行できること。置換失敗、cleanupの元cause保持、置換後reopen失敗のcommitted=trueと再open。

実ファイル010226_001はテスト作業ディレクトリへのコピーだけを操作した。欠落0参照3件を除去して音声2→章4を保持し、明示full-movie profileでtkhd/elstをduration=1605653349300のv1へ昇格した。通常タグをraw保持APIで2回保存しても15章と全mdatが一致した。ffprobeは16サンプルを表示し、先頭時刻0の空titleはstrict readerでpaddingとなる。外部原本のSHA-256不変を確認した。テストコピーはteardownで削除する。

## 未検証と制約

Windows/Linux・他CPU、AVFoundation等のplayer表示、実ファイルの生成履歴、index 0の本来のキー対応は未確定。gem公開・インストール済みbundle更新は実施していない。既存metadataを正常indexへ変換していないため、通常saveの拒否は残り、対象profileでは明示保持APIが必要。

chapter readerのco64/mdhd v1/複雑edit等の既存拒否は維持する。時間修復を全ファイルへ一般化しない。実ファイルの複数tref対応だけで完全修復できたとは扱わない。
